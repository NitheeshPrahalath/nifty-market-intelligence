Natsu, I would design this as a **market-intelligence and decision-support platform**, not merely a stock screener. The key is that every recommendation should be **explainable, trackable, backtestable, and continuously re-evaluated**.

Also, I would avoid calling any part of it “foolproof” in the financial sense. The **software architecture can be robust**, but no system can make stock predictions foolproof. The design below should explicitly account for bad data, changing market regimes, false signals, corporate actions, and model failure.


# 11. Change detection

This is where your app becomes genuinely useful.

Suppose:

```text
24 Sep

Recommendation:
BUY / ACTIVE
```

Two months later:

```text
Revenue growth ↓
EPS growth ↓
Relative strength ↓
Price < 200 DMA
Sector weakness ↑
```

The system shouldn't silently keep the old recommendation.

It should say:

> **Recommendation changed**

and explain exactly why.

For example:

```text
⚠ Thesis deterioration detected

Company:
XYZ

Previous status:
HOLD

Current status:
EXIT REVIEW

Changes:

EPS growth:
+18% → +7%

Relative strength:
Strong → Weak

Price:
Above 200 DMA → Below 200 DMA

Sector:
Positive → Negative

Reason:
Multiple independent conditions that supported
the original thesis have deteriorated.
```

That is the feature I'd consider the **killer feature**.

# 12. Exit engine

You should have several independent exit mechanisms.

### Thesis exit

Fundamentals changed.

### Technical exit

Trend invalidated.

### Risk exit

Maximum predefined loss/drawdown reached.

### Valuation exit

Stock becomes significantly overvalued according to the strategy.

### Target review

The price reaches a predefined target zone.

### Time exit

The expected holding period expires without the thesis developing.

### Event exit

Major corporate event materially changes the thesis.

Therefore:

```text
ENTRY
  ↓
ACTIVE
  ↓
MONITOR
  ├── Thesis intact → HOLD
  ├── Target reached → REVIEW
  ├── Thesis weakening → WARNING
  ├── Thesis invalidated → EXIT
  └── Time expired → RE-EVALUATE
```

# 20. Backtesting must be isolated from live recommendations

You need:

```text
Historical data
      ↓
Strategy
      ↓
Backtest
      ↓
Performance
```

and separately:

```text
Live data
      ↓
Production strategy
      ↓
Current recommendation
```

Never allow future information to leak into historical testing.

Otherwise you'll get **look-ahead bias** and false performance.

# 23. The complete project prompt

Here is the prompt I'd use as the **master specification prompt** when you start generating the actual project architecture/code/documentation.

# Nifty Market Intelligence & Stock Analysis Platform

## 1. Project Objective

Build a production-oriented stock market intelligence and decision-support application focused initially on the Indian equity market.

The system should continuously analyze stocks from:

* Nifty 50
* Nifty Midcap 150
* Nifty Smallcap 250

using historical and current market data, technical indicators, fundamental statistics, valuation metrics, momentum, relative strength, volatility, sector conditions, market-regime analysis, risk factors, and relevant corporate events.

The system must not simply generate a "BUY" or "SELL" label.

For every potential investment setup, it must provide:

* Current analysis
* Investment horizon
* Expected holding period
* Entry conditions
* Risk/invalidation conditions
* Potential exit conditions
* Reasons behind the recommendation
* Individual component scores
* Historical behaviour of the strategy
* Continuous monitoring after recommendation
* Automatic detection of changes in the original investment thesis
* Notifications when significant changes occur

The system must be explainable and auditable. Every recommendation should be traceable to the underlying data, indicators, rules, strategy version, and analysis that produced it.

The system is a decision-support and research platform, not a guarantee of future returns.

# 16. Exit Engine

Support multiple exit mechanisms.

## Technical Exit

Trend invalidation.

## Fundamental Exit

Material deterioration in business fundamentals.

## Valuation Exit

Valuation reaches a strategy-defined extreme.

## Risk Exit

Risk/invalidation threshold is breached.

## Target Review

Price reaches a predefined target/review zone.

## Time Exit

Expected holding period expires without sufficient thesis development.

## Event Exit

A major corporate event materially changes the investment thesis.

The application should explain why an exit condition was triggered.

# 25. Core Design Principle

The final system must follow this lifecycle:

DATA
↓
VALIDATE
↓
STORE
↓
CALCULATE
↓
ANALYZE
↓
COMPARE
↓
SCORE
↓
GENERATE THESIS
↓
CREATE RECOMMENDATION
↓
TRACK
↓
RE-EVALUATE
↓
DETECT CHANGE
↓
NOTIFY
↓
HOLD / REVIEW / EXIT
↓
RECORD RESULT

Every recommendation must be explainable.

Every recommendation must be historically auditable.

Every strategy must be backtestable.

Every important change must be detectable.

No prediction should be represented as certainty.

The system should optimize for transparency, reproducibility, data integrity, and useful decision support rather than simply generating frequent BUY/SELL signals.
